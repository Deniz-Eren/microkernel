# WDR_0012 — Userland utility classification: native Ring 3 vs out-of-tree CMake

```{wdr} Userland utility classification: native Ring 3 vs out-of-tree CMake
:id: WDR_0012
:status: accepted

## Context

As `libc` and the Ring 3 userland mature, the project will need more and more
userland utilities beyond the POSIX.1-2024 base set. For every new utility, a
decision must be made about how it is delivered: implement it natively inside
the repository, or integrate an existing upstream tool.

The two options have opposite costs. Implementing everything natively duplicates
mature upstream tools and adds long-term maintenance burden. Vendoring upstream
source trees into git bloats the repository, complicates third-party licensing,
and conflicts with the build-time fetch policy. A consistent decision workflow
is needed so that each utility is placed consistently as the userland grows
({need}`BDR_0003`, {need}`BDR_0004`).

## Decision

Every new userland utility is classified into exactly one of two delivery tracks
before any CMake or source work begins. The classification is made by answering
the triage decision checklist in order (see below). The two tracks are the
possible outcomes of that workflow.

### Track A — Out-of-Tree Third-Party Ports (`cmake/<pkg>.cmake`)

Portable, POSIX-compliant upstream utilities with complex file formats or
grammars (for example archives, protocols, or languages) are fetched at build
time and cross-compiled against the Ring 3 sysroot. The upstream source is never
stored in git ({need}`BDR_0003`, {need}`BDR_0004`, {need}`ADR_0054`). They are
linked dynamically against `libc.so` and the existing shared libraries
(`libz.so.1`, `libcrypto.so.3`), and each port is recorded in
`docs/THIRD-PARTY-NOTICES.md`.

### Track B — OS-Native Ring 3 Components (`/boot/ld.so`, `libc`, `bin/`)

1. Utilities coupled to kernel, ELF dynamic linker, or sysroot internals (for
   example parts of the dynamic linker, a configuration tool that manages
   library symlinks, built-in locale data in `libc`, or tools communicating with
   microkernel IPC services per {need}`ADR_0002`) are implemented natively in
   the repository.
2. Small (~150 LOC) standard POSIX wrappers (for example `getent`, `mktemp`,
   `readlink`, `uname`) are placed in `bin/`. A native C implementation (or a
   single-file BSD-licensed import) is simpler and cleaner than maintaining an
   external CMake build. The wrappers are linked dynamically against `libc.so`.

### Triage Decision Checklist

For each new utility, answer these three questions in order.

1. Does the utility depend on kernel, ELF loader, or sysroot internals, or on
   microkernel IPC? -> Track B (Native).
2. Does a portable upstream POSIX project already exist with non-trivial
   archive, protocol, or grammar logic? -> Track A (External CMake Port).
3. Is a clean POSIX implementation under ~200 lines of C with simple CLI
   semantics possible? -> Track B (`bin/`).

### Illustrative examples (not the scope of this record)

`ldd` and `ldconfig` couple to the ELF dynamic linker and sysroot, so they are
native components (Track B). `getent` is a small POSIX wrapper over NSS
functions, so it is a native component (Track B). The IANA `tzcode` tools
(`zic`, `zdump`, `tzselect`) and `tar` (via `libarchive`/`bsdtar`) have
non-trivial grammar, so they are CMake ports (Track A).

## Rejected alternatives

- Implement every utility natively in Ring 3: it duplicates mature upstream
  tools, pins the project to a fixed set of behaviors, and grows the repository
  with maintenance burden.
- Vendor upstream source trees into git: it bloats the repository, conflicts
  with the build-time fetch policy, and complicates the third-party licensing
  records.

## Consequences

- New utilities are classified with the triage checklist before any CMake or
  source work begins, so placement is consistent across the project.
- Track A utilities are added only through `cmake/<pkg>.cmake` with a pinned
  release tarball and a `docs/THIRD-PARTY-NOTICES.md` entry.
- Track B utilities live in the repository and follow the Ring 3 build rules of
  the microkernel boundary ({need}`ADR_0002`).
```
