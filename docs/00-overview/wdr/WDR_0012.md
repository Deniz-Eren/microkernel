# WDR_0012 — User-Space Utility Selection: Native Ring 3 or Out-of-Tree CMake

```{wdr} User-space utility selection: native Ring 3 or out-of-tree CMake
:id: WDR_0012
:status: accepted

## Context

When `libc` and Ring 3 user space become larger, the project must add more
utilities than the POSIX.1-2024 base set. For each new utility, authors must
select one of two paths: write it natively in the repository, or integrate an
upstream tool.

The two alternatives have opposite costs. Native code for all utilities
duplicates mature upstream tools and adds maintenance work. Upstream source
trees in git increase repository volume, complicate third-party licenses, and
break the build-time download rule. A standard decision workflow makes sure that
authors put each utility in the correct group ({need}`BDR_0003`,
{need}`BDR_0004`).

## Decision

Authors must put each new user-space utility in one of two groups before CMake
or C work starts. Authors select the group with the decision checklist that
follows. The two groups are the possible results of that workflow.

### Group A — Out-of-Tree Third-Party Ports (`cmake/<pkg>.cmake`)

CMake downloads and compiles upstream POSIX utilities with complex file formats
or grammars (for example archives, protocols, or languages) for the Ring 3
sysroot. Authors must not put upstream source in git ({need}`BDR_0003`,
{need}`BDR_0004`, {need}`ADR_0054`). CMake links these ports dynamically against
`libc.so` and active shared libraries (`libz.so.1`, `libcrypto.so.3`). Authors
must record each port in `docs/THIRD-PARTY-NOTICES.md`.

### Group B — OS-Native Ring 3 Components (`/boot/ld.so`, `libc`, `bin/`)

1. Authors write utilities natively in the repository when they use kernel, ELF
   dynamic linker, or sysroot internals. Examples are dynamic linker tools, a
   symlink configuration tool, built-in locale data in `libc`, and tools that
   use microkernel IPC services ({need}`ADR_0002`).
2. Authors put small (less than 150 lines) standard POSIX wrappers (for example
   `getent`, `mktemp`, `readlink`, `uname`) in `bin/`. Native C code (or a
   one-file BSD-licensed import) is clearer than an external CMake build. CMake
   links these wrappers dynamically against `libc.so`.

### Decision Checklist

For each new utility, answer these three questions in sequence:

1. Does the utility use kernel, ELF loader, or sysroot internals, or microkernel
   IPC? -> Group B (Native).
2. Is there an upstream POSIX project with complex archive, protocol, or grammar
   logic? -> Group A (External CMake Port).
3. Can a clear POSIX utility fit in less than 200 lines of C with simple CLI
   rules? -> Group B (`bin/`).

### Examples (Not the Scope of This Record)

`ldd` and `ldconfig` use the ELF dynamic linker and sysroot. Thus, they are
native components (Group B). `getent` is a small POSIX wrapper on NSS functions.
Thus, it is a native component (Group B). The IANA `tzcode` tools (`zic`,
`zdump`, `tzselect`) and `tar` (`libarchive` `bsdtar`) have complex grammars.
Thus, they are CMake ports (Group A).

## Rejected alternatives

- Native Ring 3 code for all utilities: it duplicates mature upstream tools and
  adds maintenance work.
- Upstream source trees in git: they increase repository volume, break the
  build-time download rule, and complicate third-party license records.

## Results

- Authors put new utilities in Group A or Group B with the decision checklist
  before CMake or C work starts. Thus, utility placement stays constant across
  the project.
- Authors add Group A utilities only through `cmake/<pkg>.cmake` with a pinned
  release archive and a `docs/THIRD-PARTY-NOTICES.md` entry.
- Group B utilities stay in the repository and obey the Ring 3 build rules of
  the microkernel boundary ({need}`ADR_0002`).
```
