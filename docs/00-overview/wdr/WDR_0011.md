# WDR_0011 — Four-Step QEMU-to-HIL Workflow for New Board Startup

```{wdr} Four-step QEMU-to-HIL workflow for new board startup
:id: WDR_0011
:status: accepted
:governs: ADR_0058

## Context

Startup of `microkernel` on new boards (Raspberry Pi 400 with BCM2711 first)
must have an automatic development loop. Manual SD-card writes, UART jumper
cables, and interactive SSH sessions do not scale for automatic agents. The host
must control the 5 V supply, image upload, and telemetry for the target at all
times. At the same time, the target must operate bare metal in RAM only.

## Decision

Use a four-step workflow for each new board. Step 1 starts the core architecture
port in QEMU and does unit tests for the isolated console protocol logic. Step 2
does one-time setup through SSH while the boot disk stays attached, then removes
the boot disk permanently. Step 3 operates the automatic host-controlled HIL
loop and does tests for the initial USB console on physical hardware. Step 4
adds native board drivers automatically through the live console.

The host side uses a board-neutral tool in `tools/hil/` controlled by one
configuration file for each board. Supply backends (`uhubctl`), image uploaders
(`rpiboot`), and telemetry readers (`dmesg`, `usbmon`, `lsusb`, and the console
device) are selectable modules. The target keeps one USB-C cable to a powered
hub and no other physical cables.

Refer to the [HIL test document](../../60-verification/hil-testing.md) and the
[Raspberry Pi 400 document](../../60-verification/hil-rpi400.md) for the full
procedure.

## Rejected alternatives

- An SD-card write loop: it must have manual host steps, wears the media, and
  cannot start an unattended target again after a hang.
- A permanent wired UART console: it breaks the one-cable layout and does not
  operate on boards without exposed UART pins.
- SSH or network debug on the target: a full network stack on bare metal must
  operate before drivers are active, which breaks the no-host-OS rule.

## Results

- Each future board uses the same framework and adds only a board configuration
  file and console adapter.
- Initial setup occurs one time and is permanent. Thus, authors must record and
  do tests for the setup steps before they remove the boot disk.
- Plan items for the first board (`TSK_0067` to `TSK_0074`) obey this workflow
  in `TASKS.md`, and the roadmap records the steps in `RDM_0010`.
```
