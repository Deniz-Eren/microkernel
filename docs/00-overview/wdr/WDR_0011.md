# WDR_0011 — Four-Phase QEMU-to-HIL Workflow for New Board Bring-Up

```{wdr} Four-phase QEMU-to-HIL workflow for new board bring-up
:id: WDR_0011
:status: accepted
:governs: ADR_0058

## Context

Bringing `microkernel` up on new boards (Raspberry Pi 400 with BCM2711 first)
needs an autonomous development loop. Manual SD-card reflashing, UART jumper
wires, and interactive SSH sessions do not scale for unattended agents. The host
must control power, image delivery, and feedback for the target at all times,
while the target runs strictly bare metal in RAM.

## Decision

Adopt a four-phase workflow for every new board. Phase 1 brings the core
architecture port up in QEMU and unit-tests the decoupled console protocol
logic. Phase 2 performs one-time provisioning over SSH while the boot media is
still present, then removes it permanently. Phase 3 runs the autonomous
host-controlled HIL loop and validates the early USB console on real hardware.
Phase 4 develops native board drivers hands-free through the live console.

The host side uses a board-agnostic runner under `tools/hil/` driven by
per-board configuration files. Power backends (`uhubctl`), image deployers
(`rpiboot`), and telemetry collectors (`dmesg`, `usbmon`, `lsusb`, and the
console device) are pluggable. The target keeps one USB-C cable to a powered hub
and no other physical attachments.

The full procedure lives in the [HIL testing
guide](../../60-verification/hil-testing.md) and the [Raspberry Pi 400
reference](../../60-verification/hil-rpi400.md).

## Rejected alternatives

- An SD-card reflash loop: it needs manual host interaction, wears the media,
  and cannot recover an unattended target from a hang.
- A permanent wired UART console: it violates the single-cable topology and
  blocks boards without exposed UART pins.
- SSH or network debugging on the target: it requires a full network stack on
  bare metal before drivers exist and breaks the no-host-OS constraint.

## Consequences

- Every future board inherits the same framework and adds only a board
  configuration file plus console glue.
- Provisioning is one-time and effectively irreversible, so the provisioning
  steps must be documented and verified before the boot media is removed.
- Planning items for the first board (`TSK_0067` to `TSK_0074`) follow this
  workflow in `TASKS.md`, and the roadmap tracks the phases in `RDM_0010`.
