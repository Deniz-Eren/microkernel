# ADR_0012 — Ring 3 Worker-Thread AIO Engine and Lock-Free aio_suspend

```{adr} Ring 3 worker-thread AIO engine and lock-free aio_suspend
:id: ADR_0012
:status: accepted

## Context

`SWR_IPC_0005` requires mandatory POSIX.1-2024 Base `<aio.h>` (`aio_read`,
`aio_write`, `aio_error`, `aio_return`, `aio_cancel`, `aio_fsync`,
`aio_suspend`, and `lio_listio`) while keeping `<mqueue.h>` behind
`_POSIX_MESSAGE_PASSING`. Moving AIO queues into Ring 0 violates `ADR_0003`.

## Decision

- Implement all `<aio.h>` operations in Ring 3 (`libc/src/aio.c`) with zero new
  kernel syscalls. Use a lazily spawned worker thread (`ThreadSpawn`) and a
  static 64-slot queue over existing descriptor I/O (`pipeserv` and console).
- Store atomic completion state (`__aio_state`, `__aio_err`, `__aio_ret`) in
  `struct aiocb` and signal completions via `g_done_seq` with `SYS_FUTEX`. This
  keeps `aio_error`, `aio_return`, and `aio_suspend` lock-free and
  async-signal-safe.
- Support `SIGEV_SIGNAL` and `SIGEV_NONE` notifications for individual requests
  and `lio_listio(LIO_NOWAIT)` batches, plus atomic `AIO_CANCELED` cancellation
  of queued requests.
- Keep `_POSIX_MESSAGE_PASSING` undefined until optional `MSG` message queues
  are implemented.

## Rejected alternatives

- Adding Ring 0 kernel AIO threads and request queues.
- Protecting `aio_error` and `aio_suspend` with a mutex (breaks
  async-signal-safety).

## Consequences

- `aiotest` verifies `aio_read`, `aio_write`, `SIGEV_SIGNAL`, `aio_cancel`,
  `aio_suspend` timeout (`EAGAIN`), `aio_fsync`, and `lio_listio` in QEMU.
- `SWR_IPC_0005` is active and checked by `posix.headers` and
  `posix.async_signal_safe`.
```
