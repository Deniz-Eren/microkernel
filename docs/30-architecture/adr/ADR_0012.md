# ADR_0012 — Ring 3 Worker-Thread AIO Engine and Lock-Free aio_suspend

```{adr} Ring 3 worker-thread AIO engine and lock-free aio_suspend
:id: ADR_0012
:status: accepted

## Context

For `SWR_IPC_0005`, the system must give POSIX.1-2024 Base `<aio.h>`
(`aio_read`, `aio_write`, `aio_error`, `aio_return`, `aio_cancel`, `aio_fsync`,
`aio_suspend`, and `lio_listio`) and keep `<mqueue.h>` behind
`_POSIX_MESSAGE_PASSING`. AIO queues in Ring 0 do not obey `ADR_0003`.

## Decision

- `libc/src/aio.c` gives all `<aio.h>` operations in Ring 3 with no new kernel
  syscalls. It starts a worker thread (`ThreadSpawn`) on the first call and uses
  a static 64-slot queue on `pipeserv` and console descriptors.
- `struct aiocb` keeps atomic status fields (`__aio_state`, `__aio_err`,
  `__aio_ret`) and wakes waiters through `g_done_seq` with `SYS_FUTEX`. This
  design keeps `aio_error`, `aio_return`, and `aio_suspend` lock-free and
  async-signal-safe.
- `libc/src/aio.c` gives `SIGEV_SIGNAL` and `SIGEV_NONE` signals for individual
  calls and `lio_listio(LIO_NOWAIT)` batches, and atomic `AIO_CANCELED`
  cancellation of queued calls.
- `_POSIX_MESSAGE_PASSING` stays undefined until the project adds optional `MSG`
  message queues.

## Rejected alternatives

- Ring 0 kernel AIO threads and queues.
- A mutex around `aio_error` and `aio_suspend`, which prevents
  async-signal-safety.

## Results

- `aiotest` does tests of `aio_read`, `aio_write`, `SIGEV_SIGNAL`, `aio_cancel`,
  `aio_suspend` timeout (`EAGAIN`), `aio_fsync`, and `lio_listio` in QEMU.
- `SWR_IPC_0005` is active, and `posix.headers` and `posix.async_signal_safe` do
  checks on it.
```
